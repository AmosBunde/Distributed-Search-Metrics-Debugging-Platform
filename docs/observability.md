# Observability

The platform watches itself with the same tools it gives its users: Prometheus
for metrics, Grafana for dashboards, Alertmanager for routing, Jaeger for
traces.

| What | Where | Notes |
|---|---|---|
| Dashboards | <http://localhost:3001> | Five, provisioned on start — no manual import |
| Alerts | <http://localhost:9090/alerts> | 9 rules, 5 recording rules |
| Routing | <http://localhost:9093> | Local routes to a no-op receiver |
| Traces | <http://localhost:16686> | Jaeger |

## Dashboards

| Dashboard | Answers |
|---|---|
| **Search Quality Overview** | Is the platform healthy right now? |
| **Anomaly Detection** | What is the detector reporting, and is it reporting too much? |
| **Service Health** | Which service is down, and what is its error budget? |
| **Kafka Throughput** | Is the engine keeping up with ingest? |
| **ClickHouse Performance** | Are inserts and queries getting slower? |

They are generated by a script rather than hand-edited, because five dashboards
of JSON share a lot of structure and hand-edited copies drift.

## Alerts

Nine rules across three groups. Two properties are deliberate:

**Every rule has a `for` clause.** A metric crossing a threshold for a single
scrape is noise, and paging on it is how people learn to ignore alerts.

**Every alert says what to do.** The `runbook` annotation is the difference
between an alert and a notification:

> **KafkaConsumerLagGrowing** — Lag that grows steadily means the engine cannot
> keep up with ingest. Parallelism is capped by partition count (ADR-0003), so
> the lever is more partitions *and* more engine replicas — adding replicas
> alone does nothing.

| Alert | Fires when | Goes to |
|---|---|---|
| `SearchLatencyP99High` | p99 > 2s for 5m | PagerDuty |
| `SearchErrorRateHigh` | gateway errors > 1% for 5m | Slack |
| `IngestRejectionRateHigh` | > 5% of events rejected for 10m | Slack |
| `KafkaConsumerLagGrowing` | lag > 10,000 for 10m | Slack |
| `MetricsEngineStalled` | events arriving, none processed | PagerDuty |
| `ClickHouseWriteFailures` | > 100 undecodable records in 15m | Slack |
| `AnomalyStorm` | > 50 anomalies in 10m | Slack |
| `ServiceDown` | a service misses scrapes for 2m | PagerDuty |
| `CollectorRateLimitingHeavily` | > 10 rejections/s for 10m | Slack |

Recording rules come first in the file so the alerts and the Grafana panels
read the same numbers: a dashboard can never disagree with a page.

## Two things this caught

**Ratios rendered "No data" instead of 0%.** With no traffic, the inner sums
produce no series and the division yields nothing — which on an error panel
reads as broken instrumentation rather than as "no errors". The recording rules
now use `or vector(0)`.

**Metric labels were unbounded.** The gateway labelled proxy requests with the
concrete path, so every trace id became its own Prometheus series — visible as
a Grafana legend with one line per trace, and eventually an out-of-memory kill.
Proxy routes now label by route template (`traces`, `debug_query`, `replay`),
and a test asserts an identifier can never reach a label again.

## Alert routing

`docker/alertmanager/alertmanager.yml` is what the local stack runs: real
routing, grouping and inhibition, with a no-op receiver. Alerts fire and are
visible at :9093, and nobody's phone rings.

`alertmanager.production.yml` is the same routing with real receivers. Secrets
are read from files rather than inlined, because Alertmanager does not expand
environment variables and a webhook URL in a committed config is a webhook URL
in git history:

```bash
kubectl create secret generic alertmanager-secrets \
  --from-literal=slack_url='https://hooks.slack.com/services/…' \
  --from-literal=pagerduty_key='…'
```

One inhibition rule is worth knowing: a service that is down will also breach
its latency and error SLOs, so `ServiceDown` suppresses the others for that
job. Paging three times for one outage is how alert fatigue starts.

## Verifying a change

```bash
promtool check rules docker/prometheus/rules/platform.yml
amtool check-config docker/alertmanager/alertmanager.yml
make dev && make simulate QPS=500
```

Then open <http://localhost:3001> — the dashboards are already there.
